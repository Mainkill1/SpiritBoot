Validated memory pin commit candidate, 2026-10-13

Product baseline 464e7ea, assembled source 04e3879e287135735111efdc8d25488d94a7793c.
Patch 0115-pin-validated-commit.patch is independent of the rejected consecutive
frame candidate. It contains no consecutive-range tracking or inferred PFNs.

Problem: the public buffer lock first validates every mapping and PFN while
holding the PFN lock. Its commit pass then calls NxkPageSupplyPin, which calls
NxkPageSupplyCanPin again for every PFN. Those second eligibility checks repeat
stable metadata tests. The existing release assembly has a nested function
call, several global/table loads, and conditional branches for each duplicate
check. The common scalar Pin routine also branches between lock and unlock.

Change: buffer locking commits through NxkPageSupplyCommitPin, which only
updates the count with the existing sticky-overflow policy. All eligibility
checks occur in the complete validation pass. Checked builds assert the
metadata invariants at the new internal helper's entry. The physical-pin API
and buffer unlock still use the original checked transitions. No relocation,
map validation, rollback, unlock, release order, stack storage, or address
translation behavior changes. The scalar pin implementation is unchanged and
therefore remains an independent oracle for the new helper's behavior.

Proof: the PFN lock stays held from the first validation through commit.
Locking modifies only count/overflow bits and cannot change a frame's bounds,
free status or RETURN_PENDING flag. Thus previously validated pages remain
eligible even when a buffer aliases the same frame repeatedly. The helper
still checks sticky overflow and sets it when the count reaches its limit;
subsequent aliases cannot wrap the count or clear a permanent pin. Invalid
requests never reach the commit pass, preserving whole-request atomicity.

The first optimization attempt tracked consecutive PFNs across the entire
buffer and regressed in initial native pairs (root reports 3.7% in the seven-pair median).
The guest uses NtAllocateVirtualMemory, not contiguous memory. NxvCommitRange
allocates page-table frames through the same page supply at 4 MiB boundaries,
so data PFNs need not be consecutive even in a clean guest. Its actual PFN
sequence was not captured. Added per-page geometry tracking was paid even
when the candidate could not avoid translations. That version is rejected.
This candidate instead removes a duplicate validation on every successful
buffer lock, independent of mapping geometry. Native performance is still a
required gate; operation counts alone are not evidence of latency savings.

Test-first: the new eligibility counter failed at the first one-page lock
(two checks instead of one). Then release and checked production-extraction
runs passed 672/672 assertions and 1,134/1,134 whole-state comparisons. ASan/UBSan
runs pass the same. Whole-state fixtures cover aliased, scattered, descending,
ascending-gap and final-gap mappings; malformed addresses/PFNs, rejection
prefixes, under-unlock rollback, deferred frees, sticky overflow and count
saturation. Free-list links, owners, heads, availability and spill hint match
the original scalar semantics. Small-vector and large retranslation counts
remain unchanged. Product host suite: 130 tests pass, three skipped.
