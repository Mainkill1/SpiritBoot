Write performance release investigation — 2026-10-13

Status: CLOSED for the original broad write-performance regression. Seven
matched native pairs do not reproduce the two reported whole-leaf regressions.
A small isolated flush timing increase remains visible in paired medians, with
overlapping ranges and mixed direction. No causal runtime defect is established
and no speculative 0119 patch is justified. Details and limits follow below.

Its HEAD alone does not identify applied patches.

Existing evidence: final three-pair campaign reports flush_buffers_visibility
7.747 -> 8.546 ms and overwrite_reextend_same_handle 16.925 -> 18.483 ms.
These are complete leaf timings, not syscall latency. Other slower leaves vary
between campaigns. This is a reason to measure focused operations, not evidence
that a specific kernel function regressed.

Frozen original fixture copies:
  tests/xbe/write-performance/frozen/{harness.h,tap.c,tap.h,io/cc_write.c,io/createfile.c}
These are byte-for-byte copies from the frozen API leaf performance fixture.
Their three replay cases are flush_buffers_visibility,
overwrite_reextend_same_handle and open_same_eof_preserves_contents.
The first measures deterministic 64 KiB pattern generation/checking, create,
write, flush, cross-handle open/read, closes, and delete. The latter two measure
128 KiB generation/checking, initial create/write/close, existing-file open,
EOF query, EOF set, second EOF query, read, close and delete. Each starts by
removing the prior path and deletes on successful completion. Initial absence
makes the first cleanup open fail normally; subsequent successful runs also
start absent. The frozen flush leaf verifies returned read length and every
byte, but does not independently query EOF. The overwrite/open controls verify
EOF before and after extension as well as read length and every byte.

Static successful original-leaf exported call counts with an absent initial
path (not dynamic internal I/O counts):
  flush: 4 NtCreateFile, 3 NtClose, 1 NtWriteFile, 1 NtFlushBuffersFile, 1 NtReadFile.
  overwrite/open: 4 IoCreateFile, 3 NtClose, 1 NtWriteFile, 1 NtReadFile,
                  2 NtQueryInformationFile, 1 NtSetInformationFile.
Both include the unsuccessful initial deletion open. No TAP output occurs
within a measured leaf.

Six separate controls measure only one operation each: written-handle flush,
64 KiB write, overwrite-open of an existing 128 KiB file, same-handle reextend
to 128 KiB, parent-directory open and close of a written 64 KiB handle. Setup
removes/recreates the same private path before every iteration. Source bytes
are deterministically regenerated. Writes use an explicit zero offset.
Verification and cleanup occur outside the operation timing. Every data case
checks returned status, read count, EOF and every byte; overwrite also checks
its disposition and the zero-length intermediate state. The parent control
checks successful open, FILE_OPENED and the Directory attribute. A failed case
invalidates the run, even if timing records remain present.

Fixture v1 runs nine cases with nine samples each, in fixed case order. Sample
zero means first invocation of that case in this process; samples 1..8 mean
warmed repetitions. These are not cold-disk measurements: earlier cases,
firmware boot, host caches and TCG translation may already warm shared code
or data. Pair campaigns must start from the identical base HDD snapshot and
alternate firmware order, keeping emulator build, machine configuration and
fixture image hash identical. A first-call-only effect and a persistent warm
operation effect have different interpretations. At least seven alternating
pairs are recommended after qualification against baseline/current/Complex.
The native runner owns asset hashes, snapshot and configuration provenance.

Raw QPC deltas (64-bit ticks) and the frequency are emitted after timing, with
81 ordered TAP assertions. tools/write_performance.py rejects missing/duplicate
captures, wrong plan, wrong sequence, wrong byte count, zero ticks/frequency,
failed correctness/TAP, missing final PASS or bad summary. It reports first
invocation and warm median/min/max separately. It does not by itself validate
firmware identity or assert a causal regression from timing.

Source investigation: the baseline-to-final runtime patch additions cover
explicit timer APC mode, validated pin commit, and DES rounds. There is no new
filesystem write/flush algorithm in that delta. The validated pin commit
removes repeated eligibility checks under the already-held PFN lock; it does
not add a write/flush. The current VfatFlushWriteThrough still traverses the
file and ancestor directory streams then FAT. NtFlushBuffersFile dispatches
to VfatFlushFile/CcFlushCache, including dirty entry update. These paths can
make total leaf cost sensitive to metadata/cache state, but this is a
hypothesis rather than a measured cause. Normal Vfat flush DPRINT sites are
disabled by NDEBUG; cache warnings are exceptional. No new write-path serial
logging was found in the runtime delta. Guest QPC includes host scheduling
and TCG translation time, so layout/cold-translation explanations also need
first-call versus warm evidence. Neither logging nor TCG is assumed causal.

The targeted whole-leaf flush ranges overlap: 7.903..9.079 ms preperf and
8.233..9.190 ms current. Their median paired difference is +0.03082 ms,
rather than the earlier campaign's roughly +0.799 ms. Overwrite warm ranges
also overlap: 14.538..15.985 ms versus 14.568..15.674 ms; its median paired
difference is -0.25989 ms, rather than the earlier roughly +1.558 ms. This
closes the original reproducible-regression concern under this frozen native
fixture. It does not prove every title workload has identical performance.

Do not erase the small flush-only observation: first-call median paired cost
is +5.038 microseconds (ratio 1.08293; 5/7 slower); warm median paired cost is
+1.630 microseconds (ratio 1.07639; 4/7 slower). First-call ranges overlap
59.27..61.94 versus 60.45..66.38 microseconds; warm per-run medians overlap
17.48..26.23 versus 20.45..23.56 microseconds. The aggregate warm current
median is slightly lower while the paired median delta is positive, showing
why both statistics are retained. This mixed, tiny control cost neither
supports the old millisecond-scale leaf explanation nor identifies a safe
runtime fix. Additional causal isolation would be required before changing
flush code.

First invocation of leaf-flush costs approximately 59.38 -> 60.36 ms, versus
~8.5 ms warm. Its median paired difference is +1.279 ms, with 5/7 slower;
first-call ranges overlap 57.84..61.49 and 59.14..64.34 ms. This is the first
file operation in the focused title and is not comparable to an original
full-suite leaf that runs after earlier I/O groups. It demonstrates a large
first-invocation effect within both firmwares. The current evidence does not
separate filesystem/host cache setup, emulator translation or host scheduling
as causes. The first-call overwrite results instead trend slightly faster
(17.691 -> 17.495 ms; ratio 0.98319; 3/7 slower). Broad write syscall controls
also show mixed direction. No additional normal-path logging or filesystem
algorithm change was identified that explains an across-the-board regression.

Closure: retain the measured small flush-control effect as a limitation;
close the original flush/overwrite whole-leaf regression as not reproduced
in seven alternating native pairs. Ship no write-path runtime change based on
this evidence. Receipt copies, file hashes, replay parser output, all raw
samples and a reproducible analysis script accompany this report in
  docs/provenance/write-performance-20261013/native-seven-pairs/
