Next SHA candidate (inspection only)

sdk/lib/cryptlib/sha1.c explicitly selects an 80-iteration rolled compression core
under SARCH_XBOX; its comment accepts lower speed to save roughly 3.8KB text.
Each round includes schedule wrapping and phase selection. Native evidence shows
SHA 1MiB was around 2.68x slower; the round core is a plausible contributor,
not yet a measured attribution. A bounded partially unrolled or phase-split core
could trade fewer branches/address calculations for resident ROM text, but must
be compared with the existing unrolled core and qualified natively. Any growth
must be audited for crossed pages and retained-patch placement as done above.

Avoid changing SHA update/context translation as part of that experiment: it has
existing observable partial-buffer writes, count carry and overlapping caller
buffer contracts covered by kernel-performance/check.py. Direct input transforms
would currently mutate input because SHA1Transform uses its buffer as a circular
schedule, so bypassing memcpy is not independently safe. No SHA implementation
change, timing experiment or speculative patch was made.
