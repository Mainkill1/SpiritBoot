### 1. XobRememberType known-type fast path

Active functions/files: `ntoskrnl/xb/obcreate.c:137`, `ntoskrnl/xb/obcreate.c:311`. Exports: 239.

**Avoidable cost:** Every repeated object create allocates a TObX node, scans the registry and frees the duplicate, even though types are never removed.

**Bounded change:** Check the existing spinlocked registry before allocating. Return if known; for unknown, allocate outside lock and retain the current duplicate recheck under lock. No object/header ABI changes.

**Correctness obligations:** Types are monotonic only within existing lifecycle. Preserve single insertion, lazy empty-list initialization, IRQL restore, callback allocation/delete/free order and silent first-registration OOM behavior; never hold spinlock across pool allocation. Avoid introducing a global success shortcut.

**Risk:** low-medium; unknown types pay an extra bounded scan, and concurrency still requires second check.

**Before/after recipe:** Guest custom type with counting allocate/free/delete procedures: create/dereference 1 and 10000 objects with same type, then 1/8/64 distinct types and two threads racing first registration. Instrument only TObX pool allocations/frees and registry comparisons. Expect repeat known-type registry alloc/free to fall from one pair per create to zero; first unknown registration remains one node. ## Findings that must stay separate from optimization

- `ntoskrnl/ob/obwait.c:510` accepts up to 64 handles in NxkWaitForMultipleObjectsMode but calls KeWaitForMultipleObjects with NULL wait-block storage. `ntoskrnl/ke/wait.c:644` rejects counts greater than THREAD_WAIT_OBJECTS with a bugcheck; `sdk/include/xdk/ketypes.h:544` defines that threshold as 3. The comment claiming stack wait blocks does not match code. This requires a separately validated correctness fix.
- `ntoskrnl/xb/xbe.c:2347` uses an untyped handle reference in XeNtReleaseMutant; its nonowner branch drops the object reference before reading SignalState. Do not treat a weaker owner/type check as an optimization. Concurrent close/lifetime and invalid-type behavior merit review.
- `ntoskrnl/xb/xbe.c:1537` returns lock-free event-cache pointers whose lifetime is tied to handle close eviction in `ntoskrnl/ob/obhandle.c:1782`. A pulse interrupted/preempted by close/reuse deserves stress characterization before expanding/indexing the cache. The fixed 64-entry table also leaves excess-created events on the pageable fallback unsafe above APC_LEVEL. No new caching proposed here.
- `ntoskrnl/xb/procobj.c:150` only reprioritizes the calling title thread, and its process list is empty; `ntoskrnl/xb/xbe.c:2637` ignores timer APC mode; interrupt synchronization without a shadow calls the callback directly (`ntoskrnl/xb/interrupt.c:135`). These are explicit existing behavior gaps, not opportunities to remove required work.
- `ntoskrnl/xb/xbe.c:327` accepts thread extension/debugger fields without honoring them, permits TLS allocation failure to proceed and notes TLS leakage on native create failure. Resource lifetime and correctness changes should be handled separately.
- PM timer wrap extension (`ntoskrnl/xb/xbe.c:1007`) depends on sampling more often than one 24-bit wrap and exclusion from higher-priority concurrent readers; do not weaken hardware reads/IRQL or infer precision from source. Physical hardware behavior was not measured.
- Custom type registration allocation failure can leave a created title type unknown (`ntoskrnl/xb/obcreate.c:137`); changing classification into unchecked header inference is unsafe. The registry is monotonic in current code, but no cleanup/removal means title relaunch/lifetime needs characterization before caching assumptions are expanded.
