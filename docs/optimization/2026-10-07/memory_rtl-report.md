## Ranked bounded opportunities

### 1. MmLockUnlockBufferPages: touched-PFN scratch cleanup

**Active path:** MmLockUnlockBufferPages -> NxkPageSupplyBeginPinBatch/RecordPin/Pin. References: ntoskrnl/xb/mm/api.c:76, ntoskrnl/xb/mm/pagesupply.c:290, ntoskrnl/xb/mm/pagesupply.c:295.

**Avoidable cost:** BeginPinBatch zeroes 2*(NxpHighestPfn+1) bytes under the PFN lock for every nonempty buffer, even one page. At 32768 PFNs this is 65536 bytes, before two translation walks.

**Bounded change:** Retain the existing USHORT multiplicity array, initially zero, and require it zero at every API exit. Track the last translated VA reaching RecordPin, including a current RecordPin that increments then rejects. For successful requests within a fixed small page budget (initial tuning example: 64 pages), clear touched PFN slots during the existing apply pass; for small rejected prefixes use a range-checked per-PFN clear helper over that prefix. For larger successful requests or rejected prefixes exceeding the budget, bulk-reset the existing entire array once at exit instead of walking the prefix again. This moves the baseline full clear from entry to exit under the same PFN lock, rather than adding a second bulk clear. No new permanent table/generation array; budget must be validated by measured crossover.

**Correctness obligations:**

- Keep the PFN lock across both translation/preflight and mutation; all-or-nothing invalid-range handling remains unchanged.
- Preserve alias multiplicity, saturated scratch counts, sticky pin overflow, pending returns, persistence, and invalid-PFN behavior.
- Clearing duplicate aliases is safe only after all preflight checks finish; include increment-then-reject and late-invalid exits in cleanup.
- No unhandled early return may leave scratch nonzero; initialization and full checked-only invariant assertions must stay outside the release hot path.
- Choose sparse/bulk fallback by translated VA-prefix length, bounding cleanup even for many aliases of one PFN. Large rejected prefixes must use one bulk reset, with no extra translation walk.

**Risk:** Medium: stale scratch after any rejection violates the next preflight; prove zero-on-entry/exit in all branches. Sparse rejection adds at most the fixed page-budget of extra translations. Large-prefix bulk fallback retains one baseline-sized clear and avoids the extra cleanup walk, but moving the clear and adding mode branches still require timing; no universal speedup is claimed.

**Before/after measurement:** Run the actual baseline and candidate kernel implementation through the exported ordinal in the same release compiler/xemu 128-MiB configuration and immutable guest ISO; at least seven paired trials, alternating order; retain all samples, median and variation. Check exact outputs/state and operation counters first; claim timing improvement only beyond observed variation. No measurements were executed in this read-only audit. Use 0/1/2/16/256/4096-page requests; unaligned ends; overflow; invalid first/middle/last page; repeated aliases to one PFN; nested lock/unlock and exact/over-count unlock; sticky overflow and deferred-free unlock. Count batch bytes cleared, translations and PFN-lock duration; expect successful small calls to clear only touched slots (two bytes per clear rather than full RAM-sized scratch); report worst-case rejection overhead too. Compare small sparse and large bulk modes around 32/64/65/128 pages and early/mid/late rejection in a 4096-page request. Large rejected prefixes should perform one full reset and zero cleanup translations; ensure aliased 4096-page prefixes also fall back. ## Limits and concerns

- This is source-guided research. Structural counts are bounds/illustrations, not measured runtime speedups. No candidate implementation or timing was executed. Kernel baselines/candidates must be measured through the real ordinal/backend in identical guests; a separate host model cannot establish latency gains.
- Candidate #1 keeps the existing multiplicity array and uses the already-required second buffer walk for successful small-request cleanup. Small early rejection adds bounded prefix cleanup; large prefixes use one bulk reset with no extra translation walk and no extra permanent scratch structure. Over-count unlock rejection occurs after scratch increment and must include the current translated PFN; clearing only previously successful records would be incorrect.
- Contended Xbox RTL critical sections are pure recursive CAS spins; behavior changes need a separate waiting/ownership/APC design and targeted contention study. Dropping atomics or adding an arbitrary yield is not proposed.
- Existing memory edges merit correctness review separately: broad system-VA MmIsAddressValid shortcut despite demand mapping; unchecked rounding/overflow in some allocators; contig reclaim retry retains a tracking slot across lock release and should be reviewed for stale-slot concurrency; VM middle-release can decommit before split-allocation failure. No fixes or behavior claims were made here.
- Shared pool reclaim repeatedly walks an entire class free list for each empty page under memory pressure. This is a concrete lower-priority work-amplification lead, but per-page indexing changes allocator metadata and needs a separate bounded design; steady-state small alloc/free is already constant-time.
- Table scans (128 big-pool entries; dynamically grown contiguous tracking; sorted VM reservations; up to 34 cache blocks; 20 error mapping ranges) were assessed individually. New hash/tree/index metadata is not automatically beneficial. Pin handling, relocation copy/PTE retargeting, zero-fill, TLB invalidation, dirty flushes, cache busy/pin ownership and persistence barriers remain mandatory.
- Actual Xbox API guest tests and clean-room pin host/guest tests were inspected for the five candidates, as detailed above. They provide direct regression coverage for pool churn, system memory, MBI/protection contracts and pin/case behavior; targeted scan/cleanup/ASCII-tail equivalence and operation-count tests remain needed. Source test existence is not evidence of execution or timing. No product research artifacts were read.
